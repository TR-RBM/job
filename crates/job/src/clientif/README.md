# Client interface

## What it does

Serves the client interface described in `docs/client-interface.md` on the service's socket. A connection whose first line is a JSON object with the single member `hello` is handed over by `daemon.rs` `handle`; every other first line stays with the service's own protocol. The connection is greeted with the version, the capabilities, the peer and the limits, and then carries any number of requests, each answered in order with `re` and one of `ok` and `error`.

It answers eleven requests: `subscribe`, `interest`, `jobs`, `job`, `tree`, `totals`, `processes`, `output`, `commands`, `command` and `native`, and `end`, which stops a running `output`. The capability list in the greeting holds exactly the eleven, and any other `op` is answered as an unknown request.

- `mod.rs`: recognising the greeting, version choice, the count of connections per user ID, reading lines within the length limit and the idle time, the envelope of answers. `Lines` reads the connection; while an `output` runs it reads ahead, keeps the requests that wait and finds the `end` among them.
- `index.rs`: the row index, one per service process. It holds a row for each of the most recently ended Jobs, 50 000 unless `JOB_CLIENT_INDEX_ENDED` names another bound (a setting for tests), the IDs of ended Jobs beyond that bound, and for every Job that has not ended its `revision` and its confirmation once read. It is filled in two places: `store.rs` calls `observe` after every save of a Job record and at recovery for every record found, and `removal` calls `removed`. `revised` gives the next `revision` of a Job, which `store.rs` writes into the record. `observe`, `learned` and `removed` are the places that emit `job` and `job_removed` changes. `learned` is called by `daemon.rs` when it takes the start time of a running Job from the supervisor's marker; it raises `revision` by one and emits the row that `observe` held back.
- `changes.rs`: the change store, one per service process: the last 8192 sequenced lines as text, the last sequence number, and the node of every Queue and Group as it was last sent. Nothing is kept before the first `subscribe` of a run. `objects` is called by `objects::Graph::save` and emits one `object` line per node whose text changed, parents first, and `object_removed`; `health` emits when the health object changed.
- `sample.rs`: the sampler, one thread that exists while at least one subscription does. Once a second it takes the service's lock three times, briefly, for the counts, the tree and the Jobs of the union of the interest sets, reads cgroup files, `/proc` and the free space after releasing it, and puts the result on a board with a tick number. It also holds the count of subscriptions per user ID.
- `subscribe.rs`: `subscribe` with snapshot, continuation and the two `resync` answers, `interest`, and the pump that a connection with a subscription runs between requests: sequenced lines from the store after the last number it wrote, sampled lines for what differs from what it last sent, the heartbeat, and `resync` when the store no longer has its next line.
- `totals.rs`: counts and capacity, and the health object.
- `row.rs`: the row, built from a Job record. It shows no termination deadline for a Job that has ended, and the network as the word of `--net`. `spell.rs`: the lowercase spellings, the one form of a source, and the Job record as it is sent.
- `jobs.rs`: `jobs`. Rows of Jobs that have not ended are built from the service's memory when asked, rows of ended Jobs come from the index; no record is read from disk. The filter, the four orders as sort keys, cursors, `at` and `ids_only`.
- `record.rs`: `job`, with the live figures read when asked. `confirmed.rs`: what the supervisor wrote when the command started (`confirmed.json` in the Job's directory, written by `shim.rs`), its short form for the row and its full form.
- `tree.rs`: `tree`, with depth and use counted in one pass over the Jobs. `measure.rs`: the counters of a cgroup, each a number or unknown.
- `processes.rs`: `processes`, from the Job's cgroup or the descendants of its supervisor.
- `output.rs`: `output` and the stopping of it, over `streams::reader`. `base64.rs`: the encoding of output bytes and of cursors.
- `args.rs`: reading the members of `args` with one wording of refusal.
- `table.rs`: `commands`, the command table of `crate::commands` as data in English or German.
- `command.rs`: `command`. It checks the fields of the request, decides whether the first words are carried, and runs job's own command code (`carry_out` in `main.rs`) under an invocation. The answer is built from what that code printed and returned.
- `invocation.rs`: the invocation, one per thread while a command is carried. It holds the working directory, the environment, the session label, the terminal size, the two sinks for standard output and standard error, and the flags the `--format json` envelope uses. The places in the command code that read the process (`call`, the working directory, `client::env`, `JOB_SESSION`, the terminal size, `println!` and `eprintln!`) ask it first. A request the command makes goes to the service's own request path in the same process, with the invocation set aside meanwhile, so the service's log lines do not land in the answer.
- `native.rs`: `native`, the passage for reading requests of the internal protocol and `Attach`. Changing requests, the output stream and the version envelope are refused.
- `service.rs`: compiled as a child of `daemon.rs` (`daemon::client_service`), because it needs the service's private state: the request path with audit, the saved environment of a Job, the totals.
- `messages.rs`: the sentences of this module in English and German.

## How to test

Run `cargo test -p job --test client_interface` through job. The cases start a private service, open its socket themselves and speak lines: the greeting and its fields, version choice and malformed greetings, the service's own first lines unchanged on the same socket, `totals` before and while a Job runs, `commands` in both languages, `command` submitting, cancelling, editing, retrying, moving and changing a Queue with the audit record and the saved environment checked, refusals and usage errors compared with what the `job` command prints, commands that are not carried, `dry_run`, `native` reads and refused changes, each request listed for `native` in the form the description shows, the terminal size of `command` and a repeated idempotency key with another specification, the line limit at and above its bound, answer order, unknown requests and the limit of 32 connections. `cargo test -p job --test client_interface_listings` covers the listings: every order paged forward and back, each filter, cursors with another filter and after a restart, `at`, `ids_only` with more than 10 000 Jobs, the bound of the index, `job` for a running, ended, retried, removed, unreadable and absent Job, `tree`, `processes`, and `output` from the start, from a position, backward, with a byte bound, with a gap, with binary bytes, followed, stopped with `end`, and of a terminal Job, the row's `network` and `termination_deadline_ms`, and output totals of streams nothing was written to. `cargo test -p job --test client_interface_subscription` covers the subscription: the snapshot, changes without a hole for two subscribers, object changes, continuation and the `resync` answers, a reader that falls behind, the interest set, the limits, listings on another connection, a filter on the snapshot's page, the `sampled` mark and a pushed `health` line. Two cases in `freezer` read the cgroup figures, ceilings and the confirmation, and the live figures of 200 Jobs of interest, inside a delegated cgroup. `cargo test -p job --test client_interface_listings listings_measure -- --ignored --nocapture` prints how long a page takes. No unit tests.
