# Comparing pressure policies

Run this benchmark through an installed job service with writable delegated CPU, memory and process controllers. It starts private daemons and leaves the installed service's configuration and state unchanged. It requires the same delegated environment as the kernel integration tests.

```sh
job run --session pressure-measurement --budget none --cores 4 --mem 4G -- \
  cargo bench --bench pressure -- --output /tmp/job-pressure-results.jsonl --repetitions 2
```

Choose a new output filename each time. The command refuses replacement and syncs each completed record. A failed run leaves earlier completed records for diagnosis; inspect the command's exit status and record count before comparing results. Each repetition produces six run records: three policies, with and without external contention. Policy order reverses on alternate repetitions. No speed threshold is a pass/fail assertion.

The benchmark does assert that all managed workloads succeed and that its required, locally supported PSI sources do not become unavailable during ordinary completion. It also rejects a waiting reason on the resource-independent outside probe. A missing-source hold or an unrelated admission barrier in this controlled environment is a qualification failure, not a policy-performance measurement.

## Workload and bounds

Each private service creates an explicitly limited Group with `cpu-limit=0.5` and `max-running=4`, containing batch and interactive Queues. A long Job consumes four CPU seconds. After three wall-clock seconds of warmup, the driver submits twelve batch Jobs consuming 100 CPU milliseconds each and three interactive Jobs consuming ten CPU milliseconds each, interleaved with those submissions. Interactive Jobs have explicit admission priority 500. An additional ten-CPU-millisecond Job in an unrelated Queue measures local hold scope. All remaining parameters are identical across policy modes.

An optional unmanaged sibling consumes three CPU seconds inside the same half-core aggregate cgroup. It shares the resource ceiling but is absent from job's workload registry. Thus a managed workload can experience pressure generated by a process outside its scheduler. This does not simulate arbitrary host-level contention or attribute pressure to its source. No global host stress, memory exhaustion or disk saturation is generated.

Each helper refuses more than four CPU seconds and aborts after 45 wall-clock seconds. Jobs also have an explicit 50-second execution limit, and each comparison has a 90-second driver deadline. Teardown kills the entire owned cgroup subtree. Slow hosts may fail these qualification bounds instead of returning a completed comparison.

## Policy inputs

| Mode | CPU some avg10 high / low | Sustain | Minimum hold | Recovery | Recovery step |
|---|---|---|---|---|---|
| none | No rule | — | — | — | — |
| sensitive | 1% / 0.5% | 1 s | 2 s | 1 s | 1 s |
| tolerant | 90% / 70% | 1 s | 2 s | 1 s | 1 s |

Both explicit rules require available measurements. These deliberately contrasting inputs are **not calibrated production profiles**. The sensitive rule explores the cost of treating ordinary CPU contention as overload. The tolerant rule measures observation/controller overhead when the activation threshold is not reached. Inspect recorded signals and events rather than assuming either mode actually activated.

## Memory workload

Select memory explicitly; the original command still selects the CPU workload:

```sh
job run --session pressure-measurement --budget none --cores 4 --mem 4G -- \
  cargo bench --bench pressure -- --output /tmp/job-memory-results.jsonl --repetitions 2 --resource memory
```

This variant adds `memory.high=48 MiB` and `memory.max=128 MiB` to the measured Group. The seed touches and holds 24 MiB for eight seconds; each batch Job touches and holds 16 MiB for two seconds. The optional unmanaged sibling holds 16 MiB for eight seconds. Helpers touch each page, then refresh the resident working set every 20 ms. Initial fault/reclaim time is included in response time; the residency interval begins after the initial page touches. Each helper still has an independent 45-second watchdog.

At most four managed Jobs and one sibling share the domain. The largest declared payload is 88 MiB (seed plus three batch Jobs plus sibling), leaving room for process overhead below the hard safety boundary. The short interactive and outside probes retain ten milliseconds of CPU work. Any memory.max, OOM or OOM-kill event fails qualification. The benchmark reads back all requested aggregate boundaries and records CPU counters, memory events and available peak memory. `memory.high` is an explicit pressure-producing throttle for this experiment; the hard safety boundary is not an admission recommendation.

Rules select memory some avg10 with the same experimental numeric high/low thresholds and timing as the table above. Inspect high events and actual signals before claiming that the workload created pressure. High events alone do not establish sustained PSI, and holding new work does not directly reclaim the memory of running Jobs. CPU and memory results are separate calibration evidence.

## Reading the artifact

The first line records environment and workload parameters; subsequent lines have `record=run` and a `result` object. Each result includes raw Job records, timestamped pressure reports, pressure events, the exact rule, and metrics:

- Makespan: earliest Job submission through latest recorded Job completion, including warmup and service lifecycle overhead.
- Throughput: completed managed Jobs divided by that makespan, in Jobs per second. The unmanaged sibling is excluded from the completion count.
- Admission wait: submission to recorded start, across all managed Jobs.
- Batch and interactive response: submission to recorded finish, grouped by workload type.
- Outside response: the single unrelated Queue probe.
- Holding entries and phase changes: actual recorded controller transitions. Multiple entries into Holding indicate renewed holds; they are not automatically evidence of an unstable controller.

Time summaries report count, mean, nearest-rank median, p95 and maximum. Three interactive samples per run are descriptive; their p95 is the maximum and is not a tail-latency guarantee. Per-Job times use the daemon's realtime timestamps; large forward clock adjustments can distort them. Run on a stable clock. Pressure observation offsets use the driver's monotonic clock. Run order, kernel, allowed CPUs, competing host load and sample size affect results.

```sh
jq -c 'select(.record == "run") | .result | {mode,repetition,external_peer,metrics}' \
  /tmp/job-pressure-results.jsonl
```

Use the data to reject policies that harm the intended workload. Memory/I/O policy calibration, host-level external pressure, repeated overload/recovery cycles and broader deployment qualification require separate evidence. See `pressure.md` for the rule and replay contracts.
